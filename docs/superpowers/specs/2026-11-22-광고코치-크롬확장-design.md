# 광고 코치 v3 — 크롬 확장 설계 (2026-11-22)

> 상태: 검토 완료, 승인 대기
> 배경 자료: [docs/2026-11-22-팀자료-정리.md](../../2026-11-22-팀자료-정리.md) (노션 팀 페이지·팀원 메모 정리)
> 표시: **[결정]** = 사용자가 정한 것 · **[제안]** = 설계자(Claude)가 정한 것, 고칠 수 있음

## 1. 무엇을, 누구를 위해, 왜

**대상**: 온라인 광고를 한 번도 해 본 적 없는 소상공인 (예: 스마트스토어에서 수제 쿠키를 파는 1인 셀러).

**하는 일**: 챗봇과 대화하면서 세 단계를 거친다.
1. **찾기**: 네이버 데이터로 "내 상품을 어느 연령·성별이 많이 찾는지", "그 사람들은 어떤 말로 찾는지"를 알려 준다.
2. **세팅**: 그 연령층과 키워드로 메타 광고 문구를 써 주고, 캐릭터가 **실제 메타 광고 관리자 화면 위를 돌아다니며** "여기를 누르세요 / 여기에 이걸 입력하세요"라고 칸마다 안내한다.
3. **분석**: 사장님이 정한 기간만큼 광고를 돌린 뒤 결과를 읽고, **무엇이 문제였는지 → 어떤 칸을 어떻게 바꿀지 → 바꾸면 수치가 어느 범위로 좋아지는지**를 알려 준다. 바꾸는 칸도 캐릭터가 안내하고, 다시 3단계로 돌아간다.

**왜 처음부터 다시 짜나** [결정]: 이전 버전(v2, Streamlit)은 기능이 쌓이며 흐름이 복잡해졌고(홈·세팅·실행·진단 4쪽, 메타+네이버 62칸), Streamlit으로는 화면을 원하는 만큼 다듬을 수 없으며, 캐릭터를 메타 화면 위에 띄울 수 없다. 목표는 **한 곳에서 한 줄로 이어지는 흐름**.

**언제까지** [결정]: BOAZ 최종 발표 **2026-12-05(토)**, PPT 15분 + 대시보드 시연. 범위는 **시연 흐름 하나를 끝까지 진짜로 동작**시키는 것으로 줄인다.

## 2. 목표 · 비목표 · 실패 조건

**목표**
- 오븐로그(수제 쿠키) 가게 하나로 ① → ② → ③ → (②로 돌아가 바꿀 칸 안내)가 끊김 없이 실제로 동작한다.
- ①은 네이버 API를 실제로 부른다. 키가 없거나 막히면 저장된 응답으로 같은 화면이 나온다.
- ②의 캐릭터는 **실제 메타 광고 관리자**에서 트래픽 캠페인 생성 흐름의 질문 칸을 차례로 짚는다.
- ③은 메타에서 내보낸 결과 파일을 올리면 진단 1개, 바꿀 칸과 값, 예상 수치 범위를 보여 준다.
- 발표용 "대시보드": ③ 결과를 큰 화면으로 보여 주는 보고서 탭.

**비목표 (이번에 안 함)**
- 네이버 광고 집행·세팅 (네이버는 조사에만 씀) [결정]
- 트래픽 외 캠페인 목표(인지도·판매), 광고 세트·광고 여러 개
- 메타 계정 연결(Marketing API, OAuth) — 파일 올리기로 시작, 나중에 붙일 수 있게만 [결정]
- 스마트스토어 주문 파일 연동 (③ 입력은 메타 결과 파일만)
- 크롬 웹스토어 등록, 로그인·회원, 여러 사용자 데이터 저장, 휴대폰
- 진단 규칙 전체 다듬기 (시연 케이스에 해당하는 규칙만 확실히)

**실패 조건 (동작은 해도 실패로 보는 것)**
- 흐름이 다시 갈라진다: 사장님이 "지금 어디서 뭘 해야 하지?"를 헤매게 되는 갈래·탭·설정 화면이 생긴다.
- 발표 중 캐릭터가 칸을 못 찾고 멈춘다 (대체 수단 없이).
- 예상 수치를 하나의 확정된 숫자로 말한다 (데이터가 작아 틀리기 쉬움, 다정 M1·M6).
- 질문이 다시 늘어난다 (희수 설계: 질문 칸 약 11개가 상한).

## 3. 제약

- 크롬(PC)만. 메타는 다른 사이트 안에 자기 화면을 넣지 못하게 막으므로(iframe 불가) 캐릭터는 **크롬 확장의 콘텐츠 스크립트**로만 띄울 수 있다.
- API 키(네이버 검색광고·데이터랩 HUB, Claude)는 확장에 넣을 수 없다 → **서버**에 둔다.
- 메타 광고 관리자는 화면 구조(DOM)가 자주 바뀌고 클래스 이름이 난독화돼 있다 → 칸 찾기 방법을 코드에 박지 않고 **안내 목록(데이터 파일)** 으로 관리하고, 못 찾으면 대체 수단으로 넘어간다.
- 시연 계정: 팀 메타 광고 계정과 오븐로그 페이지·픽셀이 이미 있음 (다정 실험).
- 일정 13일, 개발 인력은 사실상 1명(제명) + 팀원 분석 자료.

## 4. 접근 방식 (Approaches)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 크롬 확장 하나** [결정] | 사이드 패널에 챗봇, ①②③이 모두 그 안에서 이어짐. 광고 관리자 위에 캐릭터. 뒤에 파이썬 서버 | 사장님이 있는 곳이 한 군데 → "깔끔한 흐름" 목표에 가장 맞음 | PC 크롬만, 확장 설치 단계 1개 |
| B. 웹사이트 + 세팅 때만 확장 | ①③은 웹, ②만 확장 | 링크로 시작, 휴대폰으로 결과 보기 | 두 곳을 오가고 대화 상태를 두 곳에서 맞춰야 함 → 다시 복잡해짐 |
| (탈락) Streamlit 유지 | — | 기존 코드 그대로 | 캐릭터를 메타 화면 위에 못 띄움, 화면 꾸미기 한계 |

결과 받기 [결정]: **파일 올리기**로 시작. 분석 엔진은 "표준 결과 표"를 입력으로 받게 만들어, 나중에 Marketing API를 붙여도 흐름이 바뀌지 않게 한다.

## 5. 구조

```
┌──────────── 크롬 확장 (MV3) ────────────┐        ┌──────── 파이썬 서버 ────────┐
│ 사이드 패널 (React)                      │  HTTP  │ FastAPI                     │
│  - 챗봇: 단계 상태 기계 ①②③            │ ─────▶ │  /research  ← v2 market,    │
│  - 결과 파일 올리기                       │        │               naver_api     │
│  - "보고서 크게 보기" → 보고서 탭 열기    │        │  /copies    ← v2 copywriter │
│ 콘텐츠 스크립트 (adsmanager.facebook.com) │        │  /analyze   ← v2 ingest,    │
│  - 캐릭터 + 말풍선 (Shadow DOM)           │        │               metrics,      │
│  - 안내 목록대로 칸 찾기·강조·완료 감지   │        │               diagnose,     │
│ 보고서 탭 (확장 페이지, React + 차트)     │        │               rules.yaml    │
│ 저장: chrome.storage.local (대화·답·결과) │        │  키: 서버 .env              │
└──────────────────────────────────────────┘        └─────────────────────────────┘
```

**[제안] 기술**
- 확장: **WXT**(MV3 확장 빌드 도구) + React + TypeScript + Tailwind. 차트는 Recharts.
- 서버: **FastAPI**(Python 3.12). v2의 순수 파이썬 엔진(`v2/engine/`)과 사양 YAML(`v2/specs/`)을 새 폴더로 **복사해 와서** 필요한 것만 남긴다. Streamlit 의존(`st.secrets` 등)은 뺀다.
- 시연 때 서버는 노트북에서 로컬 실행(`localhost`). 배포는 비목표.
- 새 브랜치 `feat/v3-extension`, 저장소 루트에 `extension/`, `server/` 폴더. v1·v2 코드는 건드리지 않는다.

**[제안] 챗봇 방식**: 자유 대화 LLM이 아니라 **단계 상태 기계 + 버튼·짧은 입력**. 숫자·판정·바꿀 칸은 규칙 엔진, LLM(Claude)은 광고 문구 초안에만. (v2 설계 원칙 유지, 흐름이 예측 가능해야 시연이 안 깨짐.) 키가 없으면 문구는 문장 틀로 대체(v2 `copywriter` 기존 동작).

## 6. 흐름 상세

### ① 찾기 (사이드 패널)
1. 챗봇: "어떤 상품을 파세요?" → 상품명(예: 수제 쿠키), 판매처(스마트스토어/자사몰) 입력.
2. 서버 `/research`: 네이버 검색광고 키워드 도구로 연관 키워드·월 검색량 → 데이터랩 HUB 쇼핑 인사이트로 연령·성별 비중 (v2 `market.build`).
3. 화면: "**30대 여성**이 가장 많이 찾아요" 카드(연령·성별 막대) + 추천 키워드 5~10개(검색량 표시) + 출처·조회일.
4. 사장님이 확인/수정 → 다음 단계의 **타겟 연령·성별**과 **문구 재료 키워드**로 저장.

### ② 세팅 (사이드 패널 + 광고 관리자 위 캐릭터)
1. 챗봇이 문구 질문(상품 강점 1~2개) → `/copies`로 메타 문구 3안(본문·제목) → 사장님이 1개 고름.
2. 질문 칸 답 받기: 희수 설계의 질문 칸(약 11개, `meta_fields.yaml`의 `kind: question`·`precheck`)만 묻는다. 나머지는 기본값/자동 생성으로 채우고 "무엇을 기본값으로 뒀는지" 한 줄씩 보여 준다. 기간(종료일)도 여기서 정한다.
3. 결과: **세팅값 목록** (칸 → 넣을 값). 이것이 캐릭터 안내의 대본.
4. "광고 관리자 열기" 버튼 → 새 탭에서 광고 관리자 → 콘텐츠 스크립트가 캐릭터를 띄우고 안내 목록 순서대로 진행:
   - 각 단계: 대상 칸을 찾아 강조 → 캐릭터가 그 옆으로 걸어감 → 말풍선 "여기에 `30` ~ `39`를 넣으세요" (+ 값 복사 버튼)
   - 완료 감지: 칸 값이 바뀌었거나 다음 화면으로 넘어가면 다음 단계. 감지 못 하면 말풍선의 **"했어요"** 버튼.
   - 칸을 못 찾으면: 캐릭터가 화면 구석에서 "이 화면에서 ○○ 칸을 찾아 주세요" + 미리 찍어 둔 **스크린샷 안내**로 대체 (실패 조건 대응).
   - 사이드 패널에도 같은 진행 목록이 보이고 현재 단계가 표시됨.
5. 게시 버튼은 캐릭터가 짚기만 하고 **누르지 않는다** (게시는 사장님이 직접).
6. 끝나면 챗봇: "○월 ○일에 결과를 보러 오세요" + 결과 내보내기 방법 안내.

### ③ 분석 (사이드 패널 → 보고서 탭)
1. 챗봇: "광고 관리자에서 결과를 내보내 주세요" → 캐릭터가 광고 관리자의 보고서 내보내기 버튼까지 안내(안내 목록 항목으로 추가).
2. 파일 올리기(CSV/XLSX) → `/analyze`:
   - `ingest`로 표준 결과 표로 변환(메타 내보내기 화면 머리글 별칭 처리 기존 기능)
   - `metrics`로 지표 계산 → `diagnose` + `rules.yaml`로 깔때기 위부터 처음 걸린 문제 1개 (희수 7단계 파이프라인·진단 규칙)
   - 바꿀 칸과 새 값 (희수 "케이스 → 다음 달 세팅" 표, 토글·수치 단위)
   - **예상 수치 범위** (7장)
3. 사이드 패널: 결론 카드 3장 — ❶ 무엇이 문제였나 ❷ 이 칸을 이렇게 바꾸세요 ❸ 바꾸면 이 범위.
4. "보고서 크게 보기" → 보고서 탭(= 발표용 대시보드): 깔때기(노출→클릭→도착), 일별 CTR·CPM 추이, 노출 위치별 지출, 현재 vs 예상 범위, 숫자마다 신뢰 등급 배지(다정 A~D).
5. "바꾸러 가기" → ②의 4번과 같은 방식으로 **바꿀 칸만** 캐릭터가 안내 → 다시 ③을 기다리는 상태.

## 7. 예상 수치를 말하는 법 [제안]

원칙: **범위와 확률로만 말한다.** 한 숫자로 단정하지 않는다 (다정 M1·M6, 선행 연구 Lewis & Rao 2015).
- 현재 지표(CTR, 랜딩 도착률 등)는 베타-이항 사후분포로 90% 범위를 낸다 (작은 표본일수록 범위가 넓게).
- 바꾼 뒤 예상은 규칙마다 "기대 변화"(예: AN 제외 → 링크 클릭 품질 ○~○% 개선)를 사양 파일에 범위로 적고, 현재 범위에 적용해 예상 범위를 낸다. 근거가 오븐로그 실측이면 등급 `checked`, 가상 데이터·문헌이면 `hypothesis`로 화면에 표시.
- 문장 예: "클릭당 비용 **약 310~420원** (지금 450원), 좋아질 확률 **약 75%** · 근거: 가설(가상 데이터)".
- 데이터가 너무 작으면 "판단 보류 — 기간을 ○일 늘리면 판단할 수 있어요"를 결론으로 낸다(희수 규칙).

## 8. 안내 목록 (캐릭터 대본) 형식 [제안]

코드와 분리된 데이터 파일(`extension/guide/meta_traffic.json` 등). 항목마다:
- `id`: 세팅값 칸 id (`meta_fields.yaml`의 id와 같음, 예: `meta.adset.age_gender`)
- `page`: 어느 화면(캠페인/광고 세트/광고/보고서)인지 판별하는 조건(URL 조각·화면 제목 텍스트)
- `find`: 칸 찾는 방법을 **여러 개 순서대로** (aria-label → 라벨 텍스트 근처 입력칸 → placeholder → 역할+텍스트). 난독화된 클래스 이름은 쓰지 않는다.
- `say`: 말풍선 문장 틀 (`{value}` 자리)
- `done`: 완료 감지 방법 (값 변화 / 화면 전환 / 수동)
- `fallback`: 못 찾을 때 보여 줄 스크린샷 파일과 문장

시연 전날 실제 광고 관리자에서 전체 대본을 한 번 돌려 `find`를 갱신하는 것을 체크리스트에 넣는다.

## 9. 시연 시나리오 (발표용 기준선)

오븐로그 사장님 → ① "수제 쿠키" 입력 → 30대 여성·추천 키워드 → ② 문구 3안 중 선택, 질문 답 → 광고 관리자에서 캐릭터가 트래픽 캠페인 칸 안내(게시 직전까지) → ③ 결과 파일 올리기 → 진단 → 바꿀 칸 → 예상 범위 → 보고서 탭 → "바꾸러 가기"로 캐릭터가 바꿀 칸 1~2개 안내.

## 13. 빌더 검토 후 정한 것 [제안]

- **결과 내보내기는 파일 1개**: 광고 관리자 보고서에서 분석 기준을 **일 × 노출 위치**로 함께 골라 한 번에 내보낸다(도달·빈도·지출·노출·링크 클릭·랜딩 페이지 조회 열 포함). 서버가 일별 표와 노출 위치별 표로 나눠 `ingest`에 넣는다. 일별 도달은 더할 수 없으므로 주간 빈도 규칙은 일별 빈도의 근사로 계산하고 화면에 "근사"로 표시한다. 개발 첫날 실제 계정에서 이 내보내기가 되는지 먼저 확인하고, 안 되면 파일 2개로 바꾼다.
- **"바꾸러 가기"는 기존 광고 세트를 직접 수정**: 실제 사장님이 하는 방식. 수정 화면은 새로 만들기와 구조가 달라서, 안내 목록에 `mode: edit` 항목을 따로 두고 시연 케이스의 바꿀 칸 1~2개만 만든다.
- **예상 범위 사양 형식**: `rules.yaml` 각 규칙에 `expect: {metric, low, high, grade}` (상대 변화, 예: CTR +10%~+40%)를 추가한다. 좋아질 확률은 비율 지표(CTR, 랜딩 도착률)만 베타-이항 몬테카를로로 계산하고, CPC는 지출 고정 + 클릭 수 사후분포로 환산한다. 다정의 근거값이 오기 전에는 임시 가설값을 넣고 등급을 `hypothesis`로 표시한다.

## 14. 사용자에게 확인한 것

- **시연 ③ 데이터 = 오븐로그 실측** [결정] (노션 데이터 창고의 `오븐로그_메타AB_20261117-20261120.csv`와 일별 CSV 1117~1120, `server/data/demo/`로 옮김).
  - 개발 첫 작업으로 이 파일을 `ingest`·`diagnose`에 넣어 **실제로 어떤 규칙이 걸리는지** 확인하고, 그 결과를 시연 케이스로 정한다. 후보: 노출 위치(A 자동의 AN 쏠림, 1차 11/16 지출 100% AN), 판단 보류.
  - 판단 보류가 나오면 그것도 시연의 결론이 된다: "표본이 작아 단정할 수 없어요 → B가 나을 확률 ○% → 기간을 ○일 늘리기(종료 날짜 칸)"를 캐릭터가 안내. 그래서 판단 보류 경로(확률 표시 + 종료 날짜 바꾸기)를 일반 진단만큼 다듬는다.
  - 파일이 메타 내보내기 형식과 다르면(정리본 엑셀 등) 원본 CSV 기준으로 `columns.yaml` 별칭을 보강한다.
- **팀 메타 계정** [결정]: 개발 중 반복 테스트에 써도 됨, 광고 관리자 화면 언어는 **한국어 고정**, 캠페인 초안이 쌓여도 됨. → 안내 목록의 `find`는 한국어 라벨·aria-label 기준으로 만들고, 영어 화면은 지원하지 않는다(언어가 다르면 캐릭터가 "화면 언어를 한국어로 바꿔 주세요"라고 안내). 게시는 하지 않으므로 테스트 중 비용은 들지 않는다.
